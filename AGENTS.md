# AGENTS.md

LangGraph multi-agent vulnerability scanner. This repo is the **analyzer**; it scans a *separate* target repo. Not a pip package.

## Critical runtime constraints

- **Must run from this directory (the repo root).** Nearly every module uses relative paths: `settings.py` (`app_path`), `schemas.py` (`open("agents.yaml")`), `graph.py` (writes `results.json`). Importing from anywhere else breaks.
- **Target app lives outside this repo** at the location pointed by `settings.app_path` (e.g. `<target_app>` / `path/to/target/repo`). Input is its graphify-out/graph.json, produced by Graphify (automatically run in the initial phase). To switch targets, edit settings.py
- Use `./venv/bin/python` (standard virtual environment managed via `requirements.txt`). Python >= 3.11.
- Runtime external deps: `osv-scanner` must be in PATH (preprocessor scans the built container image via `osv-scanner scan image --format json`; missing → SCA silently yields nothing). **`docker` must be in PATH**: the preprocessor finds `Dockerfile`/compose files in the target repo, builds the image(s) (tag derived as `vulnscan-<dirname>:latest`), scans those, snapshots each built image's filesystem (`docker create` → `docker export` — throwaway container, never started), then starts the built container(s) in the background and writes the runtime data (`sandbox_url`, `container_name`) into `MasterState` for the validator. If no Dockerfile/compose is found, or the build fails, it falls back to `osv-scanner -r --format json` on the repo. Preprocessing is fast-pathed across runs: images are reuse-stamped by a build-definition hash (`.cache/container_builds/`; a missing stamp is backfilled when the already-present images postdate every build-definition file — pull-only compose services are exempt from that mtime test), SCA results are cached in `.cache/osv/` keyed by target identity (image content id / repo path) for `settings.osv_cache_max_age_hours` (0 disables), artifact snapshots are skipped when the image content id is unchanged, and the docker build progress is streamed into the log. The SCA scans, sandbox startup, artifact snapshot, and the AST symbol index (parallel tree-sitter via `build_symbol_index`) run concurrently on worker threads inside `preprocessor_node`. If the sandbox can't be started (or exposes no HTTP port) the preprocessor logs a warning and sets both fields to `None`; validator tools then report "no sandbox configured" and static analysis still completes.

## Running

- `./venv/bin/python graph.py` — runs the whole pipeline, dumps final state to `results.json`. Requires `<target_app>/graphify-out/graph.json` to exist (missing → prints "Waiting for actual graph.json to execute."). Each scan runs on its own checkpoint thread (pointer in `states/current_thread.txt`; a restart reruns it, while a completed scan — flagged by `states/scan-complete.flag` — makes the next start a fresh thread so old channel values never accumulate); the scan's token + pipeline-stat ledgers are likewise scan-scoped and durable (`states/token_usage_<thread>.json`, flushed on every recording; `run_stats.init_usage_ledger` is called by the entrypoint after the thread decision — a resume restores the previous processes' totals BEFORE bootstrap resets, a fresh start zeroes and drops the previous scans' files, so the Token Usage section reflects the WHOLE scan even across many Ctrl+C restarts); resuming invokes `app.invoke(Command(update=...), config)` — a plain dict input would NOT resume (langgraph starts a new run from bootstrap on non-None/dict input, which used to make every "resume" silently restart the scan). Ctrl+C is two-phase (run_stats.install_signal_handlers): the first press prints a notice and cooperatively stops once the in-flight agents finish and bank their results (queued fan-out tasks raise `run_stats.RunStopped` at entry; in-flight agents keep running to completion and their tool-loop verdicts submit normally; every completed task's durable write is skipped on the next start); the second press exits immediately, SIGTERM/SIGHUP likewise (exit 130/143, resumable checkpoints either way; forced exits leave `<attacker_container_name>-*` containers which the next startup sweeps via `attacker_tools.manager.sweep_stale_containers`).
- `langgraph dev` (langgraph.json) — exposes graphs `main`, `reviewer`, `validator`. Both entrypoints auto-load `.env` (see LLM / env below).
- Verification = import the modules: `./venv/bin/python -c "import graph, schemas, tool_loop"`.
- `tool_loop.py` holds the generic bounded-memory tool-loop machinery shared by the reviewer, validator, integration auditor and patcher (`ToolLoopAgent`, `CompactionConfig`, history splitting/transcript rendering, `_generate_agent_context_summary`, plus the base cache-hit `pre_agent`/`pre_router` driven by the subclasses' `cached_verdict` hooks, the `SequentialToolNode`, and the repeat-tool-call nudge: `ToolLoopAgent.agent` detects two consecutive identical tool-call batches (order/canonical-key-insensitive `_tool_batch_fingerprint`) and appends a transient corrective HumanMessage to the LLM-bound history only). Every loop LLM turn — including the compaction summarizer call (`_generate_agent_context_summary` books its usage to the calling agent) — writes its token usage into the per-task `token_spent` state channel (state.py `merge_token_usage` reducer), which the terminal tool / fallback persists into the cache entry. The validator's and the patcher's ToolNodes are `SequentialToolNode` (graph.py `compile_validator`/`compile_patcher`), which runs same-response tool calls one-by-one in the listed order (verified: the stock `ToolNode` fan-out races dependent batches) — this is what makes the validator prompt's "batch the script write and its launch in one response" contract and the patcher's ordered multi-hunk edit batches sound. The agent-specific subclasses, their ledger-prompt constants and module-level graph node delegates live per stage in `stage_reviewer.py` / `stage_validator.py` / `stage_integration_auditor.py` / `stage_patcher.py`.
- Code layout (monolith split): the former `nodes.py` compat facade was removed; `graph.py` imports its node/dispatch/router functions directly from the stage modules. The code lives in `llms.py` (the four ChatOpenAI instances, plus the per-invoke `UsageCapture` callback and the token-tracking `invoke_tracked` / `invoke_structured_capped` wrappers — the latter returns `(result, usage)`), `run_stats.py` (progress + pipeline-stat + per-agent **token ledgers** (`record_llm_usage`/`record_usage`/`record_cached_token_usage`/`take_cached_usage`/`add_usage`/`snapshot_token_totals`; process-local — reset with the stat ledger at bootstrap unless `init_usage_ledger`/`ledger_initialized` have pinned the durable per-scan file, see "Running"), `as_dicts`/`get_embedder`/`strip_step_numbering`/`affected_nodes_label`/`steps_block` helpers) and the stage modules: `stage_preprocess.py`, `stage_manager.py`, `stage_explorer.py`, `stage_cve.py` (`_normalize_cwe_ids` lives here), `stage_dedup.py`, `stage_threat_intel.py`, `stage_aggregate.py`, `stage_verifier.py`, `stage_edge_traversal.py`, `stage_reviewer.py` (`CROSS_BOUNDARY_VULN_TYPES` lives here), `stage_validator.py` (`route_validator_feedback` too), `stage_integration_auditor.py` (`route_integration_audit` too), `stage_patcher.py` (patch lifecycle dispatchers + `sandbox_resync_node`; its write tools live in `patch_tools.py`), `stage_reporter.py`. No stage imports another except `stage_threat_intel`/`stage_verifier` → `stage_cve`, `stage_aggregate` → `stage_cve`+dedup, `stage_reviewer` → `stage_dedup` (applying its clusters), `stage_validator` → `stage_reviewer`+`stage_patcher`, `stage_patcher` → `stage_reviewer`.
- Real entrypoints are `graph.py:graph`, `graph.py:compiled_reviewer_agent`, `graph.py:compiled_validator_agent`.

## LLM / env

- `settings.py` directly sets a unified default endpoint (`llm_base_url` / `llm_model` / `llm_api_key`) plus the **per-agent LLM registry**: `settings.llm_defaults` (model/base_url/api_key/temperature/reasoning_effort/max_completion_tokens/context_window) merged with `settings.llm_overrides[agent]`, consumed by `llms.get_llm(agent)` (build-once cache; `context_window` is config-only — `llms.get_config(agent)` exposes it, and it drives the tool-loop compaction caps via `CompactionConfig(agent)` and the explorer prompt cap) — every agent (explorer, cve_analyzer, threat_intel, contract_verifier, edge_traversal, credential_finder, compaction summarizers, dedup_agent, reviewer, validator, integration_auditor, patcher, reporter) can independently point at a different model/endpoint and run its own `reasoning_effort`; unset override keys inherit the defaults. One code path, no provider branching. The gateway config is active; the local Ollama /v1 alternative is kept as a commented-out block in settings.py.
- `llm_api_key` comes from `LLM_API_KEY` in the environment (via `os.environ.get`; missing → `ChatOpenAI` raises at first `get_llm`). `max_completion_tokens` caps and `reasoning_effort` (`none`/`low`/`medium`) are per-agent overridable kwargs (the cheap structured-JSON agents + compaction default to `none`; the reviewer/validator pairs run `low` and the reasoning agents `medium` per `llm_overrides` — the validator stays `low`: its turns produce tool calls, and the sandbox is the proof oracle — extended reasoning was pure per-turn latency).
- `.env` (gitignored) holds `LLM_API_KEY`, `TAVILY_API_KEY`, and TLS trust-store overrides (`SSL_CERT_FILE` / `REQUESTS_CA_BUNDLE`) for proxies or private CAs; external HTTPS calls can fail without them. Never commit `.env`. It is auto-loaded by `settings.py` at import time (`load_dotenv`, `override=False`, path anchored to the repo root), so every entrypoint — plain `python graph.py` included — gets the keys without shell exports. `settings.py` logs a warning naming any of `LLM_API_KEY`/`TAVILY_API_KEY`/`SSL_CERT_FILE`/`REQUESTS_CA_BUNDLE` still missing after loading; it warns, never aborts (the pipeline fails open).

## LangSmith trace splitting

Tracing itself stays env-driven (`LANGSMITH_TRACING`/`LANGSMITH_API_KEY`/`LANGSMITH_PROJECT` in `.env`). When `settings.langsmith_split_subagents` is on (and tracing active), `graph.py` wires the four tool-loop subgraphs through `run_stats.langsmith_detached_node(subgraph, agent)`: every `Send` dispatch invokes the subgraph as a **detached root trace in its own project** (`<prefix>-reviewer` / `-validator` / `-integration-auditor` / `-patcher`, prefix = `LANGSMITH_PROJECT`). Empirically verified (langsmith 0.10.5 + langchain-core 1.5.4): the root `LangChainTracer` pins the project for the whole callback tree, so nested `tracing_context(project_name=...)`, config `project_name` and `Pregel.config` are all IGNORED; the working lever (and what the factory does) is briefly clearing the `var_child_runnable_config` contextvar so the nested invoke builds a fresh callback manager whose tracer picks up `tracing_context(project_name=..., parent=False)` + `agent:<name>` tags. The parent's `reviewer_agent`/`validator_agent`/`integration_auditor` placeholder run stays in the main trace (payload inputs + verdict outputs); the detailed loop moves out. Correlation metadata rides on the invoke CONFIG (never contextvars): every run of a detached tree carries `pipeline_run_id` + `agent` + `subject` (vuln/node id via `payload_subject`); the main run's ROOT additionally gets `pipeline_run_id`/`target` from the `python graph.py` entry config (run id minted in `__main__` / `bootstrap_node`, `MasterState.pipeline_run_id` field, resume-safe — the field's `Annotated` first-non-empty-wins reducer is load-bearing: every `Command(update={"pipeline_run_id": ...})` resume patch writes into the SAME still-unfinished superstep, and un-annotated it crashes step finalization with `InvalidUpdateError` once a scan was restarted ≥2× at one step; never drop the reducer; under `langgraph dev` the platform owns the entry config so the main trace lacks it, subagent traces still correlate). Cost: the detached subtree loses the parent's other callbacks (custom tracing handlers), and node runs re-enter the subgraph via plain invoke (checkpoint-namespace inheritance kept via the config's internal `__pregel_*` keys).

## Pipeline (graph.py:82-112)

`bootstrap` → {`preprocessor` ∥ `manager`} → {`preprocessor` ⤳ `credential_finder` → `cve_analyzer` → `threat_intel_gate` ⤳ `threat_intel`, `manager` ⤳ `explorer_agent`} → `aggregate_demands` → {`contract_verifier` → `synchronization` → `edge_traversal` → `dedup_agent`} → `reviewer_agent` → `validator_agent` → `integration_auditor` → (conditional `route_integration_audit` ⇢ `validator_agent`) → `reporter_dispatch` → (`reporter` per vulnerability) → `report_assembler` → END. Validation is sequential-by-phase: `validator_dispatch_gate`/`dispatch_validators` first prove every `direct_to_validator` record; only then does `integration_audit_dispatch` run the auditor on the deferred `requires_integration` records (their chain candidates are the now-`exploitable` peers carrying proven `poc_payload`s); `chained` records go back to `validator_agent` with those peer payloads injected (`route_integration_audit`/`ValidatorState.peer_payloads`). `route_validator_feedback` (after any validator superstep) bounces `insufficient_context` records back to `reviewer_agent`; otherwise (only when `settings.patcher_enabled`) routes due-for-fix `exploitable` records to the `patch_dispatch` barrier (see "Patcher agent"), else advances to `integration_audit_dispatch`. `bootstrap` only ensures `graphify-out/graph.json` exists (runs `graphify extract` if missing) so both parallel branches can read it. `preprocessor` runs the container build/sandbox/artifact snapshot then hands off to the **credential finder** (writes `<target_app>/.cache/credentials.json` for future validator use); `preprocessor`-then-`credential_finder` dispatches CVE analyzers from `known_vulns`; `manager` dispatches explorers from `expert_tasks`; both fan out via `Send`. `dispatch_explorers` keeps skeleton (file-level) nodes unless an eligible real (non-skeleton) sibling of the same file exists in the same task — skeleton-only files (e.g. framework entrypoints or template files) must be analyzed, and lone empty skeletons are still dropped by `is_node_worth_scanning`. The Threat Intel gate conditionally dispatches CVEs needing external mechanics (no key → skips enrichment). `aggregate_demands` is reached through a single **AND-join barrier** (`add_edge(["explorer_agent", "threat_intel"], "aggregate_demands")`): a plain set of fan-in edges would trigger it on the first-arriving branch and run it twice with partial input, so the barrier guarantees it fires exactly once, only after BOTH the explorer branch and the CVE/threat-intel branch have written. To keep the barrier satisfiable, `dispatch_threat_intel`, `dispatch_explorers`, and `dispatch_cve_analyzers` each emit a stateless no-op `Send` when they have nothing to dispatch, and the corresponding node functions (`threat_intel_node`, `expert_explorer_node`, `_cve_analyzer_node`) return immediately for empty payloads. Reviewer and Validator are compiled subgraphs (see `compile_reviewer`/`compile_validator`).

The CVE analyzer (`cve_analyzer_node`) classifies each CVE into `application_mitigation` (emits a demand routed to every importing+using node, verified by the contract verifier) or `upgrade_only` (flaw lives inside the dependency — e.g. RCE in the HTTP server; emits a direct vulnerability hypothesis anchored to a synthetic `dependency:<package>` node, bypassing the contract verifier). `aggregate_demands` fans upgrade-only hypotheses straight into the `vulnerabilities` channel and they reach the reviewer directly.

Every `CVEAnalysis` also carries `required_keywords` (BOTH fix categories). At the top of `aggregate_demands_node`, `filter_cve_demands_by_keywords` (stage_aggregate.py) drops any `application_mitigation` record whose keywords are all absent from the codebase — one streaming pass over graph nodes with `file_type == "code"` (`scan_codebase_for_keywords`, utils.py; streaming per-keyword substring scan with early-exit once every keyword is found), followed by a per-record set-membership check. `upgrade_only` records are **exempt** from this pre-filter: their hypotheses are anchored to synthetic `dependency:<package>` nodes, cannot be located via app-source substrings (build-tool internals like `pip install` rarely appear in application code), and are adjudicated by the framework/dependency reviewer via container artifacts. This deterministic pre-filter runs before the contract verifier and the reviewer, so dropped records never consume LLM tokens in either stage.

## CVE analyzer upgrade-only path

- `cve_analyzer` output schema is `CVEAnalysis` (schemas.py): `fix_category` discriminates `application_mitigation` (fills `security_assumption`, routed to nodes) from `upgrade_only` (fills `hypothesis` with `cwe`/`description`/`affected_component`). Every analysis also fills `required_keywords` — strict, machine-readable code-level triggers (dotted calls like `yaml.load`, option names like `parseNested`, directives like `/next/image`). The analyzer prompt (agents.yaml CRITICAL RULE 6) forbids generic terms and the bare import namespace alone. Exactly ONE hypothesis per CVE is emitted (one analyzer per canonical CVE id, cached), so reviewer workload is bounded by CVE count.
- `deduplicate_cves` (utils.py) also carries `fixed_version`, `cwe_ids`, `severity_label`, and the CVSS v3 vector from the OSV record into `known_vulns`; the analyzer surfaces the applicable enrichment in its prompt.
- `cve_demands` cache files are keyed by CVE id only (no content hash): the new record shape does NOT auto-bust them. Delete `.cache/cve_analyzer/` to force re-classification after prompt/schema changes. Old cached records without `fix_category` are treated as `application_mitigation` (backward compatible); old records without `required_keywords` fail OPEN in the keyword filter (kept, never dropped).
- Hypotheses from this path carry `source_cve`, `demand_id=<cve>`, `vulnerability_type="Known Dependency Vulnerability"`, and a synthetic `dependency:<package>` `node_id`. They reach the reviewer's **framework/dependency** track directly.

## Threat Intel agent

`threat_intel_gate` runs after all CVE analyzer fan-out tasks complete. It dispatches one-shot Threat Intel tasks through Tavily only when a CVE is HIGH/CRITICAL (or its CVSS v3 score is at least 7.0), the analyzer dropped it, `required_keywords` is empty, or both exploit trigger fields are empty. Each search uses `f"{cve_id} {package_name} root cause writeup exploit analysis"`; the resulting web evidence and prior analysis are passed to a structured `CVEAnalysis` call. The enriched record is tagged `enriched_by: threat_intel` and replaces the original record during aggregation.

Threat Intel requires `TAVILY_API_KEY`. If it is missing or Tavily fails, the pipeline fails open and retains the analyzer result. Results are cached at `<target_app>/.cache/threat_intel/<CVE>.json`; delete that directory to force re-enrichment after prompt changes.

## Multi-track reviewer

`dispatch_reviewers` (stage_reviewer.py) routes every hypothesis into one of up to four reviewer tracks using `vulnerability_type` (`_reviewer_mode_for`):

- **code_level** (everything else — explorer/contract-verifier findings at app nodes): strict taint reachability — a concrete, verifiable data flow from an untrusted source through sanitization to an execution sink. Toolset: `read_source_code`, `read_file`, `get_node_connections`, `search_codebase`, `get_definition`, `submit_evaluation`.
- **framework_dependency** (`vulnerability_type == "Known Dependency Vulnerability"`, incl. upgrade-only CVEs): verifies exposure & active handling of the affected runtime feature/server via `search_codebase` (incl. indirect/framework usage) and config-default/transport checks through container artifacts; never expects a userland sink. Toolset: `read_file`, `get_node_connections`, `search_codebase`, `list_container_artifacts`, `find_in_container`, `read_container_artifact`, `submit_evaluation`.
- **dependency_mitigation** (`vulnerability_type == "Dependency Mitigation Vulnerability"` — contract-verifier FAILED findings for **application_mitigation** CVEs): the prefix between framework_dependency and code_level — the execution sink is trusted to live INSIDE the third-party library (CVE is established fact), but reviewers must still prove a strict first-party data flow from an untrusted source to the vulnerable library call and verify the specific missing mitigation (unsafe config, raw input passed to a dangerous API). Uses the code_level toolset (source-reading only, no container artifacts).
- **systemic** (`vulnerability_type == "Systemic Vulnerability"`): pattern-confirmation across all affected nodes; code_level toolset.
- **cross_boundary** (`vulnerability_type` in `{"cross_boundary_contract_mismatch", "differential_parsing", "confused_deputy"}` — Edge Traversal findings): verifies the composition gap between BOTH endpoints of a trust boundary (source exit profile vs target ingress profile) plus, for parsing discrepancies, the effective transport config; source-reading + container-artifact toolsets.

`application_mitigation` CVE demands are routed to nodes (as `cve_assumption` demands) and verified by the contract verifier; its FAILED evaluations are tagged with `vulnerability_type="Dependency Mitigation Vulnerability"` + `source_cve` in `_contract_verifier_node`, so these records are never folded into `systemic` grouping and reach the dependency_mitigation track.

All tracks run through the single compiled reviewer subgraph; only the system prompt (shared base + per-mode section in `agents.yaml`: `reviewer_agent.prompt` / `.code_level` / `.framework_dependency` / `.dependency_mitigation` / `.systemic`, plus the `open_questions`-only `.validator_feedback` and `patch_state == "applied"`-only `.patch_verification` sections appended by `first_turn`) and the LLM-bound tool subset differ. The subgraph's ToolNode registers the union of all toolsets, so per-mode binding is what enforces tool boundaries.

Verdict protocol (`EvaluationToolInput`, enforced by its model validator so a bad submission bounces back as a corrective ToolMessage and the loop re-answers):

- Baseline: a `false_positive` MUST carry `mitigation` — the concrete blocking defense cited to file/function/structure, and the spec requires a defense that HALTS the flow (log/warn-and-continue guards are not defenses); when the defense is an input filter/validation/whitelist/parameterization, agents.yaml directives 4 (MITIGATION COMPLETENESS) and 5 (SHARED SINK) require the text to enumerate EVERY user-controllable field/array-key reaching the sink with its guard, and to judge helpers by the sink's own merge surface (keys included), never a safe exemplar caller.
- Enumeration gates (mode-aware, enforced in `tools.submit_evaluation` because the schema is shared across tracks): `false_positive` on code_level/dependency_mitigation requires `untrusted_uses` — one entry per traced use of the untrusted value (file:line + operation + why it cannot reach a sink, derived variables and warn-and-continue branches included, the taint root identified under EVERY name the request value takes, not the stored-field name); the `systemic` track requires ≥ one entry PER `affected_nodes` member citing that node's own blocking defense, so an exemplar-instance defense cannot dismiss a bundled cluster. `framework_dependency` and `cross_boundary` FPs have no taint root to enumerate (their claims are feature-exposure and endpoint-gap), so their only structural guard is the concern bounce below; their correctness rests on the per-mode prompt rules.
- Anchoring gap: the third schema field `out_of_scope_concern` — while tracing, the reviewer must declare any source→sink flow it OBSERVED that the hypothesis doesn't cover (e.g. an untrusted upload field reaching a filesystem-deletion sink past an incomplete input-validation guard that warns but never aborts, while no hypothesis was anchored there); a `false_positive` carrying a non-empty concern is bounced ON ALL tracks until the flow is adjudicated, and on confirmed submissions the concern is persisted on the record for the Validator. Empirical note: the enumeration gate alone did NOT reliably flip such a verdict (a low-effort model enumerated only the stored field and answered the narrower question); the flip required the reviewer LLM at `reasoning_effort="medium"` (settable per-agent via `llm_overrides["reviewer"]`) — taint reachability is reasoning-bound.
- The third answer is **confirmed with reservations**: whenever a guard cannot be verified, submit `is_exploitable=true` + `direct_to_validator` with `reservations` naming each unauditable point instead of forcing either verdict; `submit_evaluation` persists `mitigation`/`reservations`/`out_of_scope_concern` on the record, and the validator's first turn renders them as REVIEWER RESERVATIONS (also per variant in batched groups; agents.yaml `validator_agent` rule 5 tells it to settle each item-by-item in the sandbox — an exploit failing exactly on a reservation is false-positive evidence) and REVIEWER OUT-OF-SCOPE CONCERN blocks.
- Reviewer submissions no longer carry `confidence_score` (the field was never in the schema, so `submit_evaluation`'s read of it was permanently null and silently dropped); `confidence_score` on records now originates only from the Integration Auditor, and the reporter labels it "Audit confidence".
- The fourth answer is the severity estimate: every `is_exploitable=true` submission MUST carry `cvss_vector` (a complete CVSS v3.x base vector; `EvaluationToolInput` bounces missing, false-positive-carried, and unparseable vectors — parseability is checked with `utils.cvss_v3_base_score`, so the pipeline's recomputed score can always be trusted). `submit_evaluation` persists it on the record (FPs keep it None — EXCEPT an FP filed while `patch_state` is set, i.e. a patch-verification verdict: there the pre-patch vector is PRESERVED, since the verdict adjudicates the fix, not the flaw's severity, and the PATCHED report section needs the real severity; model arithmetic is never trusted). The vector is a validation gate: `utils.cvss_gate_blocks` blocks every confirmed `direct_to_validator`/`requires_integration` record whose recomputed base score is below `settings.validator_min_cvss` (default 7.0; <=0 disables) — `dispatch_validators` skips such direct records, `dispatch_integration_audits` skips the deferred ones, so the sandbox is never spent on a low-severity estimate. **Boundary exception**: a gate-blocked confirmed record carrying `changes_security_boundary` (bool persisted by `submit_evaluation` from `EvaluationToolInput`; true ONLY for wire-autonomous SERVER-SIDE execution-context shifts — internal/loopback reach, tenant/entity switch, elevated backend rights, server filesystem — never XSS/CSRF/phishing) is NOT skipped outright: `dispatch_validators` still withholds the direct sandbox but `dispatch_integration_audits` takes it into its pending set for a chain-audit (shared predicate `utils.boundary_deferred`; gate-PASSING requires_integration records are never "deferred"). Its `unchainable` verdict — LLM-submitted (`submit_integration_audit`) or deterministic zero-peer (`first_turn`) — is REVOKED back to `confirmed` with an audit note, so for these records chaining is pure upside, never information loss: a no-chain outcome still falls through to the unvalidated-report rule below. The revoke is TERMINAL for the audit lifecycle: every audit outcome banks `integration_audit_reasoning` on the record and `dispatch_integration_audits` never re-pends a confirmed record carrying it (the mark-less re-pickup made the audit revoke to confirmed re-audit revoke ping-pong after every validator wave — livelock). FAIL-OPEN by design: missing/unparseable estimates (verdicts cached before vectors existed) and patch-lifecycle records always validate. A skipped record stays `confirmed` but still reaches the report — `stage_reporter._below_cvss_gate` re-applies the identical predicate in `_is_reportable`, the assembler labels the section "Validation: not performed", the prompt forbids any proven/confirmed-in-sandbox phrasing, and `_assessment_for` falls back to the Reviewer's vector when the reporter's own is malformed/missing — or when it recomputes to 0.0 on a `patch_state` record (a reportable patched finding scoring zero means the model graded the patched residual, never the flaw).

Every exploitable `submit_evaluation` sets `validation_strategy` (agents.yaml rule 6a + schemas.py `EvaluationToolInput`): `direct_to_validator` covers findings triggered directly or behind freely-attainable gates (open self-registration, a standard login any normal user performs — a plain `login_required` is NEVER `requires_integration`), `requires_integration` is reserved for privileged gates that cannot be freely registered (Admin/internal) or findings that strictly depend on ANOTHER confirmed vuln's output, and `static_finding_only` is a real-in-source finding with no network-reachable path (accepted into the report, not validated). Validation is **sequential-by-phase**: `dispatch_validators` proves every `direct_to_validator` record first and **defers** `requires_integration` records — only after that validator superstep completes does `dispatch_integration_audits` (from `integration_audit_dispatch`) fan them to the Integration Auditor, whose chain candidates are the peers now `exploitable` in the sandbox (carrying real `poc_payload`s the auditor can read). When the record has **zero other exploitable vulnerabilities to chain with**, the auditor's `first_turn` resolves it `unchainable` in place with an explanatory `integration_audit_reasoning` and a `pre_router` override ends the subgraph — no LLM call is spent and the router is never allowed to index the still-empty `messages` (`unchainable` is terminal and stays in the report, because a `chained` verdict is impossible by construction). `chained` records are re-dispatched to `validator_agent` by `route_integration_audit` with their peers' proven `poc_payload`/`execution_logs` injected via `ValidatorState.peer_payloads` (rendered as the PROVEN CHAIN COMPONENTS block), so the final exploit reuses the already-proven primitives. The auditor's `first_turn` also strips any leading `N.`/`N)` numbering the reviewer embedded in `reproduction_steps` before re-prefixing, so steps are never double-numbered.

## Container artifacts (config inspection)

The preprocessor snapshots every built container image: `docker create` (never started) → `docker export` streamed into `<target_app>/.cache/container_artifacts/<image-slug>/` with `rootfs/` (curated config/build files extracted via two passes in utils.py: the `ARTIFACT_PATTERNS` regexes for known config/entrypoint/manifest names plus a WORKDIR-scoped catch-all for small text config-like files with nonstandard names — e.g. `next.config.mjs` — that the patterns miss), `filesystem_index.txt` (curated fs path index — dependency trees excluded, sorted and bounded), `image_metadata.json` (ENV/WORKDIR/ENTRYPOINT/CMD/EXPOSE/USER/LABELS from `docker inspect`), and `extraction_summary.json`. The catch-all deliberately excludes source files (`LANGUAGE_MAP` exts), dependency trees, framework build internals (`/.next/`, maps, RSC/media payloads). It does NOT diff against the base image: that would double export I/O, still need filtering (toolchain noise), and hide base-shipped insecure defaults the reviewer needs. This keeps the reviewer's effective-config visibility decoupled from the live sandbox. The **reviewer (framework_dependency mode only)** gets `list_container_artifacts` (metadata + extracted file list), `find_in_container` (search of the curated `filesystem_index.txt` paths by name/pattern, marking which matches were extracted) and `read_container_artifact` (read_file-style paging, 150-line cap); the validator keeps its live-container tools. No builds/docker → tools report artifacts unavailable.

## Headless browser (validator)

`browser_tools.py` adds 5 validator tools (`browser_navigate`, `browser_click`, `browser_fill`, `browser_evaluate`, `browser_console`) for proving DOM / client-side vulnerabilities that `send_http_request` (which strips `<script>`) can never reach. **One shared Firefox process** (Playwright's own patched build via `channel="firefox"`; `settings.browser_executable` overrides) serves all concurrent validators; **each `session_id` gets a fully isolated BrowserContext** (cookies, storage, pages — like tabs). Concurrency/isolation contract:

- `session_id` is a required argument on every browser tool — there is NO shared "last-used" fallback. The LLM picks a unique label and reuses it across its calls.
- `agent_id` (a uuid added to `ValidatorState`, set in `dispatch_validators`) namespaces session keys as `agent_id:session_id`, so concurrent validators can never collide even with identical labels.
- **ALL Playwright object traffic is pinned to ONE dedicated browser thread** (`browser_tools.manager._browser_thread_run` → `ThreadPoolExecutor(max_workers=1)`): boot, context/page creation, cookie seeding/reading, every page op (`goto`/`click`/`fill`/`evaluate`/describe), and all teardown. Playwright's sync API binds each browser/context/page to the thread+greenlet that created it, while LangGraph's `ToolNode` runs sync tools on arbitrary workers of the shared default thread pool — without this pin a later `browser_*` call landing on a different worker would raise `greenlet.error: Cannot switch to a different thread`. The manager locks still guard the session-map bookkeeping; Playwright calls are serialized on the single worker (bounded by `browser_timeout_ms` + 30 s, failing open on timeout).
- `mark_validation_complete` and the validator `fallback` close only that agent's sessions (`browser_tools.manager.close_agent_sessions`); an idle-TTL reaper (`browser_idle_timeout_sec`, skips in-use sessions) is a last-resort safety net — all session teardown also runs on the pinned browser thread.
- Browser and HTTP channels share cookies via `ValidatorState.cookies`: the browser seeds new contexts from it and `ValidatorAgent.session_state` merges browser artifacts back, so a login done over `send_http_request` works in the browser and vice versa.
- **Fails open**: if playwright isn't installed or the browser can't launch, browser tools return "browser unavailable" and the validator continues HTTP-only (mirrors the no-sandbox fallback).

Runtime dep: `playwright` in the venv, plus its Firefox build downloaded via `./venv/bin/python -m playwright install firefox` (system Firefox is NOT juggler-patched and can't be driven). New settings: `browser_enabled`, `browser_timeout_ms`, `browser_console_max_messages`, `browser_console_msg_chars`, `browser_describe_max_chars`, `browser_executable`, `browser_idle_timeout_sec`.

## HTTP session handling & CSRF (send_http_request)

`tools.py::send_http_request` (the primary validator HTTP tool) gained three capabilities alongside redirect control:

- **Redirect cap**: `follow_redirects: bool = True` (kept) plus a new `max_redirects: int = 5`. Redirects are capped per call by mounting a `_CappedRedirectAdapter` (`HTTPAdapter` with `self.max_redirects`) on the session; exceeding the cap raises `TooManyRedirects`, which the tool's fail-open `try/except` returns as an error. `follow_redirects=False` → `allow_redirects=False`, no adapter.
- **Per-session cookies**: optional `session_id: Optional[str]`. A module-level `HttpSessionManager` (`http_sessions`, in `tools.py`) keeps plain `{name: value}` cookie jars keyed by `f"{agent_id}:{session_id}"` (mirrors `browser_tools._agent_key`), so concurrent validators picking the same label never collide. It stores jars, not live `requests.Session` objects, so each call builds a fresh request-session seeded from the jar and writes the final jar back — thread-safe across the shared ToolNode pool with no shared mutable session. First use of a `session_id` seeds from `ValidatorState.cookies`, so a login done over the browser channel (or a shared transient call) carries into the session. `session_id=None` keeps the legacy transient behavior (seed from `ValidatorState.cookies`). `reset_session=True` clears the named jar (or the shared transient state when `session_id` is omitted). The returned cookie jar is still `{name: value}`, so `ValidatorAgent.session_state` (stage_validator.py) and browser-sync merge unchanged.
- **Automatic CSRF injection**: when a form `data` field's value is a sentinel (`__CSRF__`, `__CSRF_TOKEN__`, or `TOKEN`), e.g. `data={'username':'u','password':'p','_csrf':'__CSRF__'}`, the tool GETs the same endpoint (falling back to the sandbox root) **with the same session** (so the token-page's cookie applies), extracts the token from common `<meta>` tags (`csrf-token`/`csrf_token`/`csrfToken`/`_csrf`/`authenticity_token`/`csrf-param`) or hidden `<input>`s (`csrfmiddlewaretoken`, `_token`, `authenticity_token`, `__RequestVerificationToken`, etc.), then replaces the placeholder using the discovered field name (so a wrong `_csrf` guess against Django is corrected to `csrfmiddlewaretoken`). Extracted CSRF tokens are also listed at the end of any HTML response for manual use. If a placeholder is present but no token can be fetched, the tool returns a clear error rather than sending the placeholder.

`agents.yaml` validator prompt (`validator_agent` step 6-7) teaches `session_id` reuse and the `__CSRF__` sentinel.

## Attacker container (validator shell)

`attacker_tools.py` adds 3 validator tools (`run_command`, `write_attacker_file`, `read_attacker_file`) that execute inside a dedicated Kali attacker container (`kalilinux/kali-rolling` + `kali-linux-headless`: nmap, curl, sqlmap, etc.). Lifecycle/contract:

- **Per-validator containers (isolated `/work`)**: the image is built once and shared, but EACH validator gets its OWN container named `<attacker_container_name>-<agent_id>` (`agent_id` from `ValidatorState`), with `-v <target_app>/.cache/validator/<agent_id>:/work:z` — so the container's literal `/work` is that validator's private host-backed directory (the `:z` SELinux label is mandatory on this SELinux-enforcing host: without it the bind mounts but every in-container access, even as root, fails with EACCES) and PoC files never leak between validators nor accumulate across runs. `_contains_workdir` still confines to `/work`; isolation comes from the per-agent mount.
- **Lazy provisioning**: importing `attacker_tools` never talks to docker. The image is built (hash-cached via md5 of `attacker/Dockerfile` in `attacker/.build.hash`, same idiom as `utils.build_images`) at most once, and the per-agent container is started (`docker run -d --name <name>-<agent_id> -v <host-dir>:/work:z <image> sleep infinity`) only on that validator's first shell-tool call, under a lock. A stale container holding the pinned name is replaced; afterwards the running box is reused with zero cost until teardown (`close_agent_sessions`, called from `mark_validation_complete`/`ask_for_context` and the validator `fallback`, removes it). A cache-hit validator never calls `ensure`, so no container is created. First build pulls a large image and can take minutes (`attacker_build_timeout`); `attacker/Dockerfile` pins an HTTPS distro mirror and installs `kali-linux-headless` so the build stays reproducible behind restrictive networks. Everything fails open: docker absent/build fail/start fail → tools report "attacker container unavailable" and the validator continues HTTP/browser-only.
- **Bridge + unified target URL**: the container runs on the default bridge network. The sandbox is published on all host interfaces, so it is reachable from both the host and the attacker box at the docker bridge gateway (discovered via `docker network inspect bridge`, default `172.17.0.1`). The preprocessor sets `sandbox_url = http://<gateway>:<port>` (falling back to `http://127.0.0.1:<port>` only if the gateway can't be resolved), so `send_http_request`, the browser tools, and `run_command` all share ONE target address — no loopback-vs-gateway switching. `run_command` still echoes that same URL as a `SHELL TARGET: http://<gateway>:<port>` header for reassurance. No sandbox configured → commands still run but no SHELL TARGET is printed.
- **Runtime container flags**: `--cap-add ALL` performs the actual network-level scans (nmap's low-level probes fail to even exec with Docker's default caps on SELinux-enforcing hosts, and pcap/raw sockets need more than the defaults). The container stays namespaced and non-privileged.
- **Tool surface**: `run_command(command, workdir=/work, timeout=<cap>)` runs `/bin/bash -lc` via docker exec with a hard host-side timeout and bounded output (`attacker_output_max_chars`, default 8000). `write_attacker_file` drafts PoC scripts under the validator's own `/work` (confined; escapes/absolute paths rejected). `read_attacker_file` pages them back (150-line cap) for `poc_payload`/`execution_logs` evidence. All three tools take `InjectedState` to resolve the calling validator's container; `send_http_request`'s `files=` path reads attacker-written bytes via `read_attacker_file_bytes(path, state)`, so it targets the same per-agent container. An exploitable `mark_validation_complete` carrying `poc_script` (workdir-relative path of the final script in `/work`) reads the script bytes out of the still-running container before teardown and stages them at `.cache/poc_scripts/<vuln_id>/<rel>` (variants' clones inherit the field) — the reporter bundles them into the report's `poc/` dir. Thread-safe lock on lazy boot; single-validator concurrency means virtually no exec contention.
- **Prompt**: the validator system prompt (`agents.yaml` step 7) teaches the unified target URL — the `Target Sandbox` is the bridge gateway and `run_command`'s `SHELL TARGET:` header echoes that same URL, so no address switching is needed. The attacker tool binding lives in `ValidatorAgent.bind_tools` (stage_validator.py) and is gated behind `settings.attacker_enabled`; the ToolNode union in `graph.py::compile_validator` also registers them (the LLM schema from `bind_tools` is the source of truth, so nothing breaks when `attacker_enabled=False`). New settings: `attacker_enabled`, `attacker_image_tag`, `attacker_container_name` (a name *prefix*), `attacker_workdir` (container mount point), `attacker_command_timeout`, `attacker_build_timeout`, `attacker_output_max_chars`. Delete `attacker/.build.hash` (or set `force_rebuild`) to force an image rebuild after Dockerfile edits.

## Credential finder (preprocessing)

`credential_finder.py` is a single-shot (non-looping) preprocessing node wired as `preprocessor → credential_finder → dispatch_cve_analyzers`, so it runs after the container build/sandbox-start/artifact-snapshot phase completes (it never touches docker or graph state; it just reads `settings.app_path` and the artifact cache and writes a file). It discovers **pre-configured credentials** and persists them to `<target_app>/.cache/credentials.json` (always written, empty list when nothing is found).

- **Deterministic collectors** (no LLM, fail-open): dotenv files (`KEY=VALUE` with credential-ish keys, paired by namespace so a shared-prefix account pair — e.g. a database user key and its database password key — merges); compose files (`services.*.environment` map/list + `env_file:`, `${VAR}` interpolated against repo dotenv map); Dockerfiles (`ENV`/`ARG`); SQL statements buffered to `;` (`CREATE USER ... IDENTIFIED BY`, `SET PASSWORD FOR ...`, `GRANT ... TO ...`); application source/seed files — `password_hash('<lit>')` defaults (with nearby `'name' =>` pairing), `define('KEY', 'v')` and generic `KEY = 'v'`/`'key' => 'v'` assignments whose key is secret-like (tokenized key test, so `tokenizer`/`csrf_token`/`password_expiration_delay` are NOT flagged), plus `.sql` files; container artifacts — `image_metadata.json` `Env` vars and credential-bearing files (`*.env`, entrypoints, `*.conf`, `initdb.sql`, ...) under each image's extracted `rootfs/`. Values must look like literals (no `$(...)`, PHP concat, escaped quotes) and non-placeholder. Manifest/lockfiles (`MANIFEST_NAMES`) and excluded paths are skipped.
- **Optional LLM normalization**: when `credential_finder_use_llm` is true (default), ONE structured `CredentialList` call (agents.yaml `credential_finder` prompt) labels/dedupes the raw candidates into `{service, kind, username, secret, source, notes}`. Cached at `.cache/credential_finder/<content-hash>.json` keyed on the raw candidates. Fails open to the raw candidates on any error.
- **Settings**: `credential_finder_enabled`, `credential_finder_use_llm`, `credential_finder_max_file_bytes`, `credential_finder_max_scan_bytes`. The file is consumed by the Validator: `credential_finder.authentication_block()` (fail-open) renders the records into a `TARGET AUTHENTICATION` block (one bullet per credential — `username`/`password` when an account is known, else the bare secret — each suffixed with the record's `notes`), which `ValidatorAgent.first_turn` injects into its first-turn user prompt so the agent can authenticate when the exploit needs a session.
- **Coverage note**: the deterministic repo walk (compose `environment`/`env_file`, `.env` templates, Dockerfiles, SQL seed files, application source defaults) is the primary recovery channel and must never be skipped: on many containerized applications the credentials are injected at runtime through compose/env rather than baked into the image, so the built-image `Env` (`image_metadata.json`) alone frequently yields nothing while the repository-side harvest recovers the full set (pre-seeded application accounts, database superuser secrets, and infrastructure secrets alike).

## Edge Traversal agent (cross-boundary composition)

`edge_traversal` (graph.py; `edge_traversal_node` in stage_edge_traversal.py) is a **single synchronous node** running on the linear chain `synchronization → edge_traversal → dispatch_reviewers`, so its findings land in the `vulnerabilities` channel before reviewer dispatch — no extra fan-out/AND-join barrier. It detects composite vulnerabilities that only exist when individually-benign components interact across a trust boundary.

- **Boundary-edge synthesis** happens deterministically (no LLM) in `boundary_edges.py` (see `boundary_edges.md`):
  - *Direct cross-community AST edges*: `relation in {calls, references, imports}` with `community(u) != community(v)`; `imports` is included because monolithic applications (front-controller / AJAX entrypoint scripts reaching into a shared `src/` class layer) couple almost entirely through imports. Low-signal reference/import targets (exceptions, loggers, utils, pure-type helpers) are pruned; optional note-scoping (`edge_traversal_require_note`) keeps only edges touching at least one node with an explorer interface note.
  - *Async messaging*: join queue/event dispatch call sites (`send_task`, `.delay()`, `.apply_async()`, `publish`, `basic_publish`, literal event names) to worker/board registrations (`@app.task(name=..)`, `@shared_task`, `@receiver(..)`) on the normalized name.
  - *Internal HTTP*: join HTTP-client call sites (`requests`/`httpx`/`axios`/`fetch` with a URL literal) to web route registrations (`@app.route`, express `app.get`, Django `path`) via URL-pattern matching.
  - *Infra-to-app*: parse reverse-proxy configs (`nginx location … proxy_pass`, Apache `<Location>/ProxyPass`) from the container artifacts and match the proxy prefix/upstream path to app routes.
- **Batching**: `cluster_boundary_edges` groups surviving edges by boundary category (order: infra, async_messaging, network_ipc, in_process) into homogeneous batches of `edge_traversal_batch_size` (5–10), capped at `edge_traversal_max_batches`; per-category candidate capping prefers edges with notes on both endpoints. One structured `EdgeTraversalOutput` LLM call is spent per batch (batches cached at `<target_app>/.cache/edge_traversal/<fingerprint>.json`, keyed on the serialized batch incl. note profiles + artifacts). The whole deterministic synthesis itself is disk-cached next to the batches (`synthesis_<fingerprint>.json`, fingerprint over graph file mtime/size + edge/exclusion settings + full note map + container-artifact proxy-config state), so resumes and repeated runs skip the minutes-long edge re-synthesis entirely; the fingerprint tracks graph.json/settings/notes/artifacts but not the target source bytes, so delete that directory to force fresh synthesis after hand-editing target code without re-running graphify extract.
- **Output**: `findings` (each `affected_nodes=[u, v]`, `vulnerability_type` ∈ the three composite classes, `cwe_id`, `gap_details`, `validation_strategy`) convert to standard hypotheses and route to the reviewer's `cross_boundary` track; `assertions` (edge invariant flags — upstream validation satisfies downstream demands) are logged as pruning evidence, not emitted as findings.
- Settings: `edge_traversal_enabled`, `edge_traversal_batch_size`, `edge_traversal_max_batches`, `edge_traversal_{direct,queue,http,infra}_enabled`, `edge_traversal_require_note`, `edge_traversal_max_edges_per_category`.

## LLM dedup agent (hypothesis clustering before the reviewer)

`dedup_agent` (graph.py; `dedup_agent_node`/`apply_agent_clusters` in stage_dedup.py) is a single synchronous node on the linear chain `edge_traversal → dedup_agent → dispatch_reviewers`; its clusters ride in `MasterState.hypothesis_clusters` and dispatch_reviewers applies them before the `Send` fan-out, so a merged duplicate is never reviewed, never validated and never reported — the exact precedent of the embedding merges (the duplicate records stay untouched `hypothesis` records in the channel). Catches what the embedding pass cannot: reworded duplicates and the same shared-callee defect re-anchored under different caller nodes.

- **Grouping (deterministic)**: FIRST the node runs `embedding_dedup` (the shared helper wrapping `dedup.py::cluster_vulnerabilities` the reviewer dispatch also uses) over every `status == "hypothesis"` record, so the cheap deterministic embedding pass collapses near-verbatim twins before any LLM token is spent — floods reach grouping with fewer copies. Grouping then takes the surviving records with a `vuln_id`, EXCLUDING `Known Dependency Vulnerability` (one per CVE by construction, and cross-CVE merges would drop a finding — also hard-enforced at apply time by splitting clusters on `source_cve`). Key = `cwe_id` (missing → `UNKNOWN`); groups over `dedup_agent_group_max` (50) are ordered by (**full source directory**, file names excluded, synthetic `dependency:`/`infra:` nodes and app-root files in a coarse `_root`) then `vuln_id` and cut into **balanced near-cap chunks** (`dedup_agent_max_group` (50) per call; the chunking never strands a too-small tail except a literal 1-record one from pathological configs, which the <2 filter drops fail-open — that record just dispatches un-deduplicated): directory locality is a SORT KEY, not a partition, so small sibling directories co-pack into one call and cross-directory duplicates compete in the same prompt. Chunk groups label `bucket` with the chunk's distinct depth-1 dirs (`install+js`, max 3 then `+Nmore`) for the log line, prompt header and fingerprint; sub-cap groups stay `bucket=""` vuln_id-sorted (fingerprints stable). Groups below 2 records are skipped (no possible duplicate). `dispatch_reviewers` re-derives the SAME `embedding_dedup` survivors (same function, same channel order, disk-cached embeddings ⇒ same result, so no merge state crosses between the two stages) before `apply_agent_clusters`.
- **The agent**: NOT a tool loop — one structured `DedupAgentOutput` call per group on `get_llm("dedup_agent")` (`method="json_schema", strict`), groups run concurrently (`dedup_agent_parallel`). Payload per record: verbatim `vuln_id`, ≤8 affected-node ids, description truncated to `dedup_agent_desc_chars` (900 — cutting a verifier text mid-`Evidence:` would hide the discriminating sink call) — the hashed group fingerprint covers exactly that rendered content + the dedup agent's effective `model`/`reasoning_effort` from the LLM registry. The model returns disjoint equivalence classes (`member_vuln_ids` ≥2 + `reason`); unknown ids are filtered at the node. Batches cached at `<target_app>/.cache/dedup_agent/<sha256>.json`; output-cap failures are uncached (re-attempted next run) and counted as `dedup_agent_groups_skipped_output_cap`. Fails open: a group's call erroring dispatches its records un-deduplicated.
- **Apply (in `dispatch_reviewers`, AFTER `cluster_vulnerabilities`)**: proposed clusters are transitively closed (union-find), intersected with the records surviving the embedding pass, split on differing `source_cve`; the canonical (systemic type preferred — its per-node enumeration gate absorbs the twins — then most affected_nodes, then lowest vuln_id) gets the ordered `affected_nodes` union plus `agent_merged_from`; duplicates are dropped from the dispatch list. The canonical's changed content busts its reviewer cache once (by design). Stats: `dedup_agent_groups`, `hypotheses_merged_by_agent` (+ report rows).
- **Prompt** (`agents.yaml` `dedup_agent`): merge same sink/location, single-change root causes, records anchored to DIFFERENT callers that all feed the SAME unguarded shared callee (the fix lives once in the callee — verified to collapse a shared-callee IDOR cluster re-reported across several caller endpoints into one), and records reporting ONE AND THE SAME protective control ABSENT at every call site along a single protected operation's call chain (a missing rate-limit reported at the public entrypoint AND at the underlying authentication chokepoint = one absence fixed once at the chokepoint — the empirical miss that let an unthrottled-authentication finding reach reviewer/validator/patcher as several separate records); never merge different guards/paths, DIFFERENT operations independently lacking the same class of control (login vs password-reset throttling), different CVEs, or generic-risk rhymes; unsure ⇒ keep separate (over-merging hides findings). Prompt/desc-budget edits do NOT bust the group cache — delete `.cache/dedup_agent/` after editing them. `dedup_agent_enabled=False` makes the node inert.
- **Where descriptions come from**: explorer-note hypotheses carry the mandatory `Hypothesis.description` (schemas.py — one-to-two sentences naming input + exact sink call + missing guard; explorer_prompt rule 1 forbids param/CWE-title-only text). `stage_explorer._extract_hypotheses` falls back to the bare `component` label (`md5`, `SQL Injection`, …) for notes cached under the old 3-field schema — the notes cache is keyed by node content and prompt/schema edits do NOT bust it; delete `.cache/notes/` to get the rich texts. Contract-verifier FAILED records arrive as `Fails to satisfy demand: '<demand>'. Evidence: …` — one demand replicated across N callers yields verbatim-identical texts at different nodes, which is exactly the shared-callee signal the prompt tells the agent to merge. A systemic record whose mandatory `pattern_label` was nonetheless omitted by the model now loses its short signature fallback (description is a long sentence → falls to node-independent CWE-level grouping) instead of the old component-label sig.

## Reviewer ⇄ Validator feedback loop (insufficient context)

The validator has a dedicated terminal tool, `ask_for_context` (tools.py, schema `AskForContextInput`), separate from `mark_validation_complete`. It flags a record `insufficient_context` (with `open_questions` + `reasoning` stored in `execution_logs`) when the validator cannot reach a verdict because the report left it unable to test — no reachable sandbox/route, ambiguous reproduction steps, or missing auth/session details (N.B. an exploit that merely fails is a false positive, not a context problem). `graph.py` routes `validator_agent` through `route_validator_feedback` (stage_validator.py): flagged records within `settings.validator_feedback_max_rounds` (default `1`) are `Send` back into `reviewer_agent` as a fresh subgraph whose first turn renders `open_questions` as a "VALIDATOR FEEDBACK (INSUFFICIENT CONTEXT)" block and attaches the `reviewer_agent.validator_feedback` agents.yaml section to the system prompt (the feedback rule is no longer a standing core directive — first-pass prompts stay byte-identical); the reviewer must resolve each question and re-emit self-sufficient `reproduction_steps`. The `reviewer_agent → dispatch_validators → validator_agent` edge then re-runs validation; terminal verdicts (`exploitable`/`false_positive`) do not loop, so the cycle drains. When nothing is flagged, `route_validator_feedback` advances to `integration_audit_dispatch`, so a re-reviewed record that re-entered `confirmed` + `requires_integration` is re-audited (re-chained) before its next validation pass.

**One-ask enforcement**: `ValidatorAgent.terminal_tool` is the tuple `("ask_for_context", "mark_validation_complete")` (ToolLoopAgent handles `str | tuple` terminal tools — loop ends and countdown message lists all of them). `bind_tools` binds `ask_for_context` **only when `report_to_test.review_round < validator_feedback_max_rounds`** — i.e. only on the first pass. After the reviewer re-answers (round > 0) the tool is removed from the validator's toolset, so the agent physically cannot request context again; the system prompt (`agents.yaml` step 7) instructs it to conclude with `mark_validation_complete` on the available evidence on that final pass. `ask_for_context` never sets a verdict; `mark_validation_complete` no longer handles feedback (it is a pure `exploitable`/`false_positive` terminal driven by `is_confirmed`). **Replay drains** (the cap alone did not drain — a cached ask replayed forever): the ask verdict IS validator-cached, so `ValidatorAgent.cached_verdict` REFUSES a cached `insufficient_context` on any pass where `ask_for_context` is no longer bound (`not _is_first_pass` — the exact binding predicate; a round>N report must run live and conclude via `mark_validation_complete`); when a cached ask legitimately replays onto a still-first-pass report (the tool is bound there, e.g. a round-0 report or a patched record that never asked), `ValidatorAgent.pre_agent` stamps `review_round = report.review_round + 1` onto the applied record (mirroring the pre-cache live bump — un-bumped, the merged seed stayed at round 1 and `route_validator_feedback` re-flagged it on every superstep, ping-ponging reviewer↔validator for hours, each cycle a cache-exempt ~17-turn reviewer run); and the router fires after EVERY validator superstep while earlier re-reviews are still in flight, so a process-local `(vuln_id, review_round)` claim (`utils.take_feedback_dispatch` — a wrapper over the generic `utils.take_dispatch_claim` below; the claim set is cleared by `clear_feedback_dispatch_state()` at bootstrap next to `clear_warning_state()`) makes each record dispatch its re-review exactly once per round.

- New `VulnerabilityRecord` fields: `open_questions` and `review_round` (incremented on each context request). The reviewer cache is content-hash keyed on the report, so the added `open_questions`/`review_round` bust the hash and force a genuine re-review.
- `merge_vulnerabilities` ladder: `insufficient_context` (4) ranks above `confirmed` (2) AND above the auditor's intermediate `chained` (3) — the Validator's `ask_for_context` verdict must DISPLACE `chained` (an equal rank made the tie-merge discard the ask and its bumped `review_round`, so the record stayed `chained` forever and `route_integration_audit` re-dispatched it after every validator wave — livelock). `exploitable` (5) ranks above them all. A reviewer re-answer (`confirmed`/`false_positive`/`exploitable`/`review_error`) replaces an `insufficient_context` record unconditionally.

## Patcher agent (auto-fix + re-verification)

`settings.patcher_enabled` (default **False** — with it off every patch hook is inert and the pipeline behaves byte-identically to before) adds a **bounded fix loop** between validation and the integration audit: `route_validator_feedback` routes `exploitable` records (`stage_patcher.needs_patch`: `patch_state` in {None, `"rejected"`}, `patch_round < settings.patcher_max_attempts` (default 2), not `Known Dependency Vulnerability`/`Systemic Vulnerability` — their sinks are vendor-internal / cluster-wide) to the `patch_dispatch` barrier → `dispatch_patchers` fans one **PatcherAgent** tool-loop (stage_patcher.py, `get_llm("patcher")`, cached in `.cache/patchers/`) per record. A retry re-entry needs NO extra wiring — a rejected attempt leaves the record `exploitable` + `patch_state="rejected"`, so the same route redispatches it; the patcher's first turn then renders "Patch attempt: N of M" + a PRIOR PATCH ATTEMPTS block (summaries/diffs/outcomes from `VulnerabilityRecord.patch_history`, which `submit_patch` appends to before overwriting the patch_* fields; the rejected outcome quotes the tail of `execution_logs`). The loop reuses `read_source_code`/`read_file`/`search_codebase`/`get_definition` plus two write tools (`patch_tools.py`):

- `patch_source_file(file_path, start_line, end_line, replacement)` — the ONLY write capability: replaces a line range (numbering from the agent's own reads) under a process-wide lock, confined to first-party paths (`is_path_excluded` refused), steered by SOFT minimalism budgets (~6 hunks / ~40 lines per hunk; module constants in patch_tools.py, never hard caps — a budget is applied anyway and only its FIRST crossing bounces back as an advisory note in the tool reply, stamp persisted on the `patch_log` entry so resumed runs stay quiet), with an idempotence guard (range already equals the replacement → counted as applied, no byte change — replay-safe) and echoed OLD-LINES + unified diff so a wrong range is visible immediately; the ToolNode is `SequentialToolNode` so multi-hunk batches apply in listed order.
- `submit_patch(summary)` — terminal: banks `patch_summary`/`patch_diff`/`patched_files` (diff = pure concatenation of the hunks' unified diffs, so `patches/<vuln_id>.patch` stays mechanically apply-able; no-op-replay notes only when nothing changed textually), archives the superseded attempt into `patch_history`, bumps `patch_round`, sets `patch_state="applied"` and status back to `confirmed` (bounces with empty `patch_log`; the give-up path = stop tool use and let the iteration-cap `fallback` write `patch_state="failed"` + keep `exploitable`; `failed` is TERMINAL, `rejected` retries while budget lasts). Both outcomes go through `cache_patcher` so a resume never re-applies edits to already-patched files.

**Patch state machine**: `applied` → `reviewed` (`tools.submit_evaluation` flip on the re-review) → `verified` (validator: exploit dead + legitimate flow healthy; status `false_positive`) | `rejected` (exploit still fires; status back to `exploitable`; retry-eligible) | `failed`. A reviewer `false_positive` on the patched code is NOT the deliverable proof: `dispatch_validators` additionally picks up every `false_positive` + `patch_state=="reviewed"` record (individually, never batched) so the validator's rule-7 re-test decides `verified` vs `rejected`.

Then `route_patch_reviews` → `sandbox_resync` node (`utils.resync_sandbox`, deterministic): **Tier 1** rebuild-from-source targets (`Dockerfile`/compose `build:`) force-`build_images` + `start_sandbox` (patched COPY) and re-probe the port; **Tier 2** otherwise (pull-only stock images, e.g. a service that just pulls a prebuilt database/web app image) `docker cp` each patched file into the LIVE `sandbox_container` — path verified against the pre-patch tree (WORKDIR + common roots + bounded basename `find`), never blindly created — plus one `docker restart` (survives opcache/in-memory runtimes; volumes/installed state intact); **Tier 3** fail-open note. The outcome string rides `MasterState.sandbox_resync_note` (and updated `sandbox_url`/`sandbox_container`) into every validator payload. `dispatch_patch_reviews` then Sends the applied records back to `reviewer_agent`; the re-review is cache-exempt (`is_feedback_review` returns True whenever `patch_state` is set) and its first turn dynamically attaches the `reviewer_agent.patch_verification` agents.yaml section to the system prompt PLUS the PATCH APPLIED user-message block (verdict on the PATCHED code, no feature disabling; first-pass reviewer prompts stay byte-identical). `tools.submit_evaluation` flips `patch_state` "applied"→"reviewed", which drains `route_patch_reviews` — no patch loop. A re-confirmed record goes through the NORMAL validator dispatch again: patched records always validate ALONE (`dispatch_validators` excludes them from `(cwe, component)` variant batching) and get the PROPOSED PATCH + SANDBOX SYNC block (`ValidatorState.sandbox_resync_note`) plus the `validator_agent.patched_target` agents.yaml section (appended to the system prompt under the same `patch_diff` condition — standing validator prompts stay byte-identical) — replay the PoC (still firing ⇒ fix failed, stay `exploitable`), then smoke-test the legitimate flow (FP only when exploit dead AND app healthy; a broken app is NOT a fix; unsynced sandbox ⇒ dynamic result inconclusive-for-patch). `merge_vulnerabilities` has lifecycle rules on top of the status ladder: a patcher write (patch_state applied/failed), a `reviewed` re-answer onto `applied`, and a validator `verified`/`rejected` verdict all replace unconditionally (the ladder's FP>exploitable precedence alone would strand them). The preprocessor persists `sandbox_container` and starts compose with `--force-recreate` when the flag is on, so a previous scan's CP'd container layer can never pre-patch this scan. Report: patched records get a deterministic `#### Proposed fix` section (summary, verdict line keyed on `patch_state` — verified dynamic proof / rejected-after-N-attempts / statically adjudicated / failed-abstract — and diff) and a bundled `patches/<vuln_id>.patch`; a `false_positive` carrying `patch_diff` with `patch_state` reviewed/verified is reportable via `stage_reporter._is_patched_closure` — its section documents the ORIGINAL (pre-patch, dynamically-proven) flaw, NEVER the fixed state as a "false positive": the finding PDF carries a bold `**Status: PATCHED**` banner and the glance-table title gets a `**(PATCHED)**` marker, the reporter prompt demands the UNPATCHED scoring (C:N/I:N/A:N / 0.0 explicitly forbidden there), and `_assessment_for` re-scores such a 0.0 vector back to the record's preserved pre-patch estimate (header counts stay "Auto-patched & verified" / "Auto-patched, statically adjudicated"); stats `patcher_records`/`reviewer_patch_rechecks` plus state-derived patch-attempt and verified rows.

## Reporter agent (final report)

The reporter phase is a **fan-out**: a terminal barrier `reporter_dispatch` receives every early/terminal exit — `dispatch_reviewers` (no hypotheses), `dispatch_integration_audits` (no pending audit), `route_integration_audit` (nothing chained), plus the unused `__end__` branches of the other conditional maps — then `dispatch_reporters` emits **one single-shot `reporter` task per reportable vulnerability**. The `reporter` node's outgoing edge is the fan-out barrier, so `report_assembler` runs once after all per-vulnerability tasks complete and writes **THIS SCAN's report directory** `report_<YYYY-MM-DD_HHMMSS>/` (main `report.pdf` + one self-contained PDF per finding under `findings/` — see "Output" below). ONE directory per scan: the name is minted by the first assembler write and banked in `MasterState.report_dir`, and any later arrival (the feedback/chaining loops can re-trigger the terminal dispatchers while an earlier wave is still in flight — an assembler run does not cancel sibling branches) wipes and re-renders the SAME dir, so the last wave wins with the fullest record set instead of leaving duplicate partial reports. When nothing is reportable, `dispatch_reporters` routes straight to `report_assembler` (still writing a statistics-only "no findings" report).

- **Reportable set**: a record with `status == "exploitable"` OR (`status == "confirmed"` AND `validation_strategy == "static_finding_only"`) OR a CVSS-gate-skipped `confirmed` record (the reviewer's estimate fell below `settings.validator_min_cvss`, so it was never validated — reported with an explicit "Validation: not performed" line and forbidden any dynamically-proven phrasing) OR a patch-verified `false_positive` (`patch_diff` + `patch_state` reviewed/verified — the auto-verified fix itself is the deliverable); everything else (other false_positives, unchainable, review_error, unproven confirmed) is excluded.
- **Single-shot, per vulnerability**: each `reporter` task takes ONE record (`ReporterState.report`) and spends ONE structured `ReporterFinding` call on `get_llm("reporter")`. Output = a concise `title` (few-word section heading, schema-described so no prompt edit), a short `summary` (distilling `description` + reviewer reasoning), `reproduction_steps` rewritten from the validator's `poc_payload`/`execution_logs`, a CVSS v3.1 base `cvss_vector` (the prompt shows the Reviewer's pre-validation estimate as the starting point and tells the reporter to correct metrics the proven reproduction contradicts; gate-skipped records additionally get NEVER-proven phrasing instructions), `worst_case_scenario`, and `remediation` (one line + minimal fenced snippet). The node attaches `vuln_id` deterministically and appends to the `reporter_findings` channel. The LLM sees the PoC/logs as ground truth but the prompt forbids quoting them.
- **Assembler**: `report_assembler_node` maps findings to records by `vuln_id`, computes each CVSS base score deterministically via `cvss_v3_base_score` (utils.py) and re-derives the severity label via `cvss_severity_label` (the model's own `severity` is only a fallback for a malformed vector; a missing/malformed finding vector first falls back to the record's Reviewer `cvss_vector`), severity-ranks the sections, and writes the report.
- **Output**: `<target_app>/report_<YYYY-MM-DD_HHMMSS>/` (one dir per scan — see the overwrite rule above; repo-root `results.json` is untouched) is SPLIT into a MAIN `report.pdf` plus one PDF PER FINDING: `<report_dir>/findings/<NN>_<vuln-id-slug>/report.pdf` (NN = severity rank from `_ranked_rows`, slug = sanitized vuln_id capped at 60 chars so paths never overflow a page), making each finding directory self-contained. All PDFs render via `_markdown_to_pdf` (markdown-it-py + weasyprint; needs system pango/cairo). The MAIN report contains the header counts, the **Pipeline Statistics** section, the **Token Usage** section (per-agent LLM calls/input/output/total tokens + grand total, `_build_token_usage` from `snapshot_token_totals`) and the severity table "Findings at a Glance" (# / Title / CVSS / Severity / Report — no CWE column, CWE lives in each finding PDF's metadata block) whose extra **Report** column points at each `findings/.../report.pdf` (long folder names abbreviated in the cell, and `_soft_break` injects zero-width-space wrap points into title/path tokens so no unbreakable token can ever stretch the table past the page margins — done through the markup because overflow-wrap on cells triggers the weasyprint 70 row-drop bug; poppler strips the ZWSPs, so the text layer extracts clean; the real folder keeps the full slug) — it carries NO `## Findings` detail sections. Each finding PDF is headed by its `title` and carries the metadata block (ID/CVSS vector+score/CWE/type/affected nodes/source CVE/audit confidence — only when the Integration Auditor set it/PoC + patch file names/"Validation: not performed" note), the reporter's **Summary** and rewritten **Reproduction steps**, a `## Worst-case impact` block answering "what is the worst thing that could happen if a malicious actor exploits this vulnerability?", and `## Remediation`; patched records append the deterministic `#### Proposed fix` block (see "Patcher agent"). `_bundle_finding_artifacts` writes each record's runnable PoC script into its OWN `poc/` dir (the bytes staged by the validator under `.cache/poc_scripts/<vuln_id>/<rel>` — see "Attacker container" — rebuilt from the record's `poc_payload` text when the staged file is missing, e.g. validator cache hit, skipped when neither exists) and any `patch_diff` into its `patches/<slug>.patch`; a PoC script or diff is ALSO reproduced inline in the finding PDF only when it fits `_fits_inline` (≤20 lines, no line over 90 chars, no embedded fence), otherwise the report only references the bundled file. There is **no Executive Summary**, and the raw `description`/`reviewer_reasoning`/`poc_payload`/`execution_logs` are deliberately **not** written to the report (the reporter distilled the first two into `summary` and the last two into the steps).
- **Statistics provenance**: the section mixes values derived from the final `MasterState` (notes, grouped demands, record statuses, `reporter_findings` count, CVSS-gate skip count) with run-local counters (`_pipeline_stats` in run_stats.py) recorded at the stage boundaries where each count is knowable — `_record_stat` in `dispatch_reviewers`/`route_validator_feedback`/`dispatch_validators`/`dispatch_integration_audits`/`route_integration_audit`/`dispatch_patchers`/`dispatch_patch_reviews`/`dispatch_reporters` (task fan-outs) and in `_contract_verifier_node` (evaluation verdicts) and in `dedup_agent_node` (group calls). Reset at `bootstrap` so repeated runs in one process do not accumulate — but only while no durable scan ledger is pinned: under `python graph.py` both ledgers are flushed to `states/token_usage_<thread>.json` on every recording (`record_usage`/`_record_stat`) and restored on resume, so the report of a multi-restart scan shows the earlier (stopped) processes' counters and token spend too, not just the last live process's. Stats are never derived from LLM output. The report's **Token Usage** section comes from the separate per-agent token ledger (run_stats.py): single-shot agents record usage directly from `invoke_structured_capped`/`invoke_tracked` (the `UsageCapture` callback sees usage even through `with_structured_output`); tool-loop agents sum usage via the per-task `token_spent` channel and record every turn live; and every cache HIT books the entry's persisted usage, so a fully-cached run still reports the work behind the verdicts (a cached verdict stores `{calls, input_tokens, output_tokens}` inside its entry file alongside the record — `_cache_stored_record` in utils.py wraps as `{"record": …, "token_usage": …}`, legacy bare-record entries still read and restore nothing; raw `cache()` payloads carry a `token_usage` sibling key that `take_cached_usage` pops on read so it never pollutes hashed/channelled dicts).
- **Cache**: `.cache/reporter/<vuln_id>_<content-hash>.json` (`cache_reporter`, utils.py) keyed on the single record (including its `poc_payload`/`execution_logs`, so a changed validator proof busts it); a hit returns the stored `ReporterFinding`. The assembler always re-renders, so the statistics stay current. If a reporter task's structured call throws, that task fails open to the record's own description/steps rather than losing the finding. Delete `.cache/reporter/` to force fresh assessments.

## Deduplication and validation batching

Five layers stop the same real vulnerability from being adjudicated N times (`dedup.py`, `stage_dedup.py`, `utils.py`, `stage_reviewer.py`, `stage_validator.py`). Thresholds were tuned offline against embeddings from representative real-world scans (see comments in `settings.py`); the decisive measurement: hub-callee hypotheses anchor on bare parameter names (`$str`, `$itemtype`) whose token identity is meaningless (cosine ~0.6 between utterly different defects), while genuine paraphrase duplicates sit at cosine ≥ 0.93 even with low component overlap.

- **Demands** (before the contract verifier): `deduplicate_demands` merges per-target paraphrases (exact normalized identity, then embeddings at `demand_dedup_threshold` = 0.86 on the description text alone — adding callee/source tokens would add a shared prefix that compresses similarities and admits MORE false merges). It first canonical-sorts each target's demands (`_canonical_demand_key`): channel arrival order follows parallel explorer completion, and the contract-verifier cache keys (whole-node md5 of the ordered list, positional batch slices) plus the embedding cluster seeds are order-sensitive — unsorted, the hub nodes re-hashed and recomputed their biggest prompts every run. `cve_assumption` demands never merge; upstream demands merge on exact identity only.
- **Hypotheses** (before reviewer fan-out): `cluster_vulnerabilities` — dependency records (`source_cve`) pass through untouched; identical-node-set duplicates merge at `semantic_dedup_threshold` (0.80); CROSS-node code-level duplicates need the two-tier gate `_pair_mergeable_fast`: cosine ≥ `dedup_cross_node_similarity` (0.93; in the 0.93–0.95 band a ≥0.4 jaccard sanity check applies when BOTH anchors are descriptive — `HIGH_CONFIDENCE_COSINE` 0.95 in dedup.py merges on the embedding alone — and bare-identifier anchors also merge on embedding alone), or cosine ≥ `dedup_anchor_confirmed_similarity` (0.85) plus a strong descriptive component (jaccard ≥ `dedup_anchor_min_jaccard`). Degenerate anchors (short bare labels without structural punctuation — `is_degenerate_anchor`; structural selectors like `request_params['filter']` / `$db->prepare()` and 3+-word prose count as identifying, mirroring the validator's `_validation_group_key` token convention) never justify a cross-node merge by themselves, and per-cluster CROSS-NODE membership is capped at `dedup_max_merged_cluster` (25; same-node duplicates exempt) so hub-parameter floods can't coalesce into one oversized review. Embeddings are chunk-batched and disk-cached at `.cache/hypothesis_embeddings/`; the whole stage fails open to exact-identity merging.
- **Hypotheses** (before reviewer fan-out, LLM layer): the `dedup_agent` node (stage_dedup.py — see "LLM dedup agent") runs AFTER the embedding pass above (it collapses through the same `embedding_dedup` helper first) and clusters the survivors by `cwe_id` (+ dir-ordered packing for big CWE groups), one structured LLM call per group returning true-duplicate equivalence classes the embeddings cannot see (reworded duplicates, same shared-callee defect anchored to different callers); `apply_agent_clusters` in `dispatch_reviewers` keeps one canonical per cluster (systemic preferred, affected_nodes unioned, `agent_merged_from` provenance), duplicates never dispatched. Cached per group fingerprint, fails open on any error; `dedup_agent_enabled = False` disables the layer (the embedding pass then runs only in `dispatch_reviewers` again).
- **Channel reducer**: `merge_vulnerabilities` still merges on exact `vuln_id` (systemic records get node-independent ids, so they keep collapsing on their own).
- **Confirmed → validator** (non-destructive): `dispatch_validators` batches records whose `(cwe_id, normalized vulnerable_component)` match EXACTLY — never embeddings, because one shared run's verdict is written to every member — into a single `ValidatorState` whose first turn renders an EQUIVALENT VARIANTS block (all steps + affected-node sources; every member's nodes included). Short pure-identifier anchors never batch; groups above `validator_variant_max_group` stay individual; `validator_records` counts dispatched validation runs (Sends), not member records. `tools.propagate_validation_update` clones the terminal verdict (`exploitable`/`false_positive`, plus per-member `review_round` bumps on `insufficient_context`) onto every member's own `vuln_id`; `fallback` gives each member its own timeout note; a seed cache hit re-fans through current `validation_variants` (`ValidatorAgent.pre_agent` override). No record is ever dropped or text-merged — each keeps its own report section.
- **Dispatch claims & sandbox health gate**: every status-based fan-out dispatcher (`dispatch_validators` direct + rule-7 re-test, `route_validator_feedback`, `route_integration_audit`, `dispatch_integration_audits`, `dispatch_patch_reviews`) selects on channel STATUS and fires again on every later superstep of any sibling task, so while a record's own agent run is in flight its status is unchanged and each re-firing would burn a second full agent run on the same record; `utils.take_dispatch_claim(*key_parts)` (process-local locked once-per-key set, cleared by `clear_feedback_dispatch_state()` at bootstrap so resumes re-dispatch) suppresses those duplicates — each call site's key embeds exactly what a LEGITIMATE re-dispatch changes (`review_round` / `patch_round` / chained peer-set). `dispatch_validators` peeks (`utils.dispatch_claim_taken`) while selecting and commits claims only after the sandbox probe, so an aborted dispatch never burns claims for records that never went out. `take_feedback_dispatch` is the feedback-specific wrapper. Additionally `utils.ensure_sandbox_reachable(sandbox_url, phase)` runs before the validator/auditor fan-outs and RAISES (`SANDBOX UNREACHABLE …`) when the checkpointed sandbox answers no HTTP at all, instead of spending LLM tokens on runs that can only observe a dead target and caching their garbage verdicts; raising (not skipping) keeps the run resumable at the same step with records untouched. `merge_vulnerabilities` has one status-ladder escape hatch, `_force_reset` (popped from the update before merge, replaces the stored record verbatim) — used only by out-of-band recovery tooling to re-open verdicts banked against a broken sandbox.

## Demand routing (node resolution)

`utils.parse_call_target` splits explorer-note targets (`Class::method`, `module.method`, chained fluent `getInstance()->display()` calls, and variable-receiver method chains like `var->method`) into `(module, symbol)`; bare function names stay moduleless (the legacy split put them in `module` with symbol `"unknown"`, so every global-function lookup failed the file-match leg — this was the bulk of the old DOWNSTREAM DROP churn). Used by `stage_aggregate._route_downstream` and `_route_upstream`, both of which pass the analyzing node as `caller_node_id`. `utils.resolve_node_id(module, symbol, caller_node_id=None)` with a module/class hint runs the legacy file-match scan but prefers strict label forms over the substring leg, and after a miss walks the class's bounded ancestor closure (inherits/extends/implements/mixes_in) so methods merely inherited by the hinted class resolve from the defining ancestor rather than the hinted subclass. Moduleless/bare lookups are GLOBAL-EXACT ONLY — unique normalized-label hit, or exactly one function-style label among same-label candidates (global alias vs. identically-named class members); a widely-inherited bare method name (the same identifier defined on dozens of unrelated classes) stays unresolved by design rather than misroute a demand to a random class. A `parent`/`self`/`static`/`this`/`$this` module with a caller id resolves inside the caller's container (`build_container_members`; `parent` via direct inheritance edges, `self`/`static`/`this` via the bounded ancestor closure, mirroring PHP's own `self::` lookup — the old resolver had no caller context and dropped all such targets). Container membership (`build_container_members`/`_member_map_from_graph`, also driving `_repair_call_edges`) comes from the graph's `method`-relation edges, with the legacy `<class_id>_<method>` id convention only as fallback — graphify's collision-avoidance renames class nodes (so a class id and its member ids no longer share the legacy prefix convention), which silently orphaned a large set of member-id classes (`Change`, `Ticket`, …); `_resolver_indexes` additionally registers every class-relation endpoint in `class_by_label`/`by_stem` even with zero member nodes, so empty subclass declarations (`class SomeLeaf extends SomeBase {}`) stay hintable and the ancestor walk reaches the real member on the defining ancestor. A class hint that names one of the caller's ancestors falls back to the caller's own container (explorers sometimes tag `self::` calls with the parent the method is inherited through). `resolve_node_id` never logs misses: it returns `(node_id, miss)` with `miss` a `(code, detail)` pair — `global-none`/`global-ambiguous`/`class-absent` are expected (builtins, vendor code, deliberate anti-guess) and `_route_downstream` logs them at INFO; only `method-absent` (hallucinated method / misattributed static receiver) is a WARNING. The upstream routing call treats a miss as normal (the caller-invokes-symbol filter is the oracle; nothing logs unless the demand truly qualifies for no caller). Resolution logs (downstream drops, upstream scope drops) fire ONCE per unique target per run via `utils.warning_once`/`info_once`, cleared by `clear_warning_state()` in `bootstrap_node` alongside the stats ledger. Counters `demand_nodes_resolved_fallback`, `resolve_targets_unresolved_unique`, `demands_dropped_unresolved_unique`, `demands_dropped_scoped_unique` render as report stat rows when nonzero. Routing content keys the contract-verifier's whole-node hash, so any resolver change busts the verifier cache of affected nodes (one-time re-verification — that's the point).

## Gotchas

- **Everything is cached** in `<target_app>/.cache/{notes,cve_analyzer,threat_intel,contract_verifier,reviewer,validator,integration_auditor,patchers,edge_traversal,dedup_agent,reporter,demand_embeddings,hypothesis_embeddings,osv,container_builds,poc_scripts}` (utils.py `cache()`; the two `*_embeddings` dirs are per-(model,text) hash caches consumed by dedup.py; `poc_scripts/` is the validator-staged PoC-script payload consumed by the reporter). Keys are content hashes of the demands/report/batch, except the CVE analyzer and Threat Intel caches, which are keyed by CVE id. The `osv/` cache (SCA results, keyed by image content id / repo path) and the `container_builds/` stamps (build-definition hashes enabling image reuse) are TTL/hash based instead — see "Critical runtime constraints". Delete any of these subdirs to force fresh work. The four verdict caches plus the reporter cache store their payload wrapped with the producing run's `token_usage` (see "Statistics provenance"); legacy (pre-wrapping) entries still read fine and restore no tokens. Schema/prompt edits do NOT bust caches (batch evaluations are stored as raw dicts, never re-validated): the `DemandEvaluation.reasoning` → `evidence` rename renders old cached batches as `Evidence: None` — delete `.cache/contract_verifier/` after verifier schema/prompt changes.
- Reviewer cache files are content-hash keyed on the hypothesis report only — prompt, tool, artifact, or `EvaluationToolInput` schema changes do NOT bust them (`VulnerabilityRecord` fields are different: the merge reducer dumps the full model, so the newer `cvss_vector` field stamped a new key into EVERY hypothesis dict and busted every reviewer entry on the first run after it landed — one-time and by design). For selective re-adjudication after a verdict-protocol change, grep the directory for the record's `vuln_id` and delete those files; delete `.cache/reviewer/` only for a full re-review pass.
- Validator and Integration Auditor caches (`cache_validator`/`cache_integration_auditor`, utils.py) are content-hash keyed on the record being tested plus its peer payloads/chain candidates (`sandbox_url` deliberately excluded — docker reassigns the port each run; `cvss_vector` is likewise stripped recursively from the hashed payload of these two caches AND `cache_patcher` via `_strip_cvss_key`, so the reviewer's incidental estimate never forces sandbox re-validation nor replays a banked patch — the reviewer/reporter caches deliberately do NOT strip it). Verdicts are written through on `mark_validation_complete`, `ask_for_context`, `submit_integration_audit`, the deterministic no-peers `unchainable` resolution, and both loop-fallback paths; a hit short-circuits in `pre_agent` and ends via the agents' empty-`messages` `pre_router` guard. A changed toolset/prompt or an altered proven peer payload do NOT bust them. Delete `.cache/validator/` / `.cache/integration_auditor/` to force genuine re-validation/re-audit. The validator cache stores only the batch SEED's verdict — on replay the cached verdict is re-fanned to whatever the CURRENT grouping put in `validation_variants`, so a batch membership change does not stale-lock the members.
- Container-artifact snapshots (`.cache/container_artifacts/`) are keyed on the image's docker content id (stamped into `extraction_summary.json` as `image_id`): a preprocessor re-run whose images carry the same id reuses the snapshot, while rebuilt images get a fresh `docker export`. Snapshots predating the image_id stamp (or without a readable one) re-extract once and get stamped; stale snapshots for images no longer built are removed.
- Preprocessor writes `.ast_symbol_index.json` into the target app dir; the `get_definition` tool reads it. It is not committed in this repo.
- Reviewer `read_file` reads a line range of a file on the host relative to `settings.app_path` (for files not in the graph, e.g. `Dockerfile`), capped at 150 lines. The validator reads files *inside* the sandbox via `run_command` (attacker container) or `send_http_request`; do not confuse the host-side `read_file` with those.
- `VulnerabilityRecord` auto-derives `vuln_id` (node_id:CWE:anchor; Known Dependency Vulnerability records anchor on the CVE id — `node:CWE:<source_cve>` — so distinct CVEs on one package never collide); `merge_vulnerabilities` (utils.py:372) dedupes by it with a status-priority ladder and never text-merges records from two distinct source CVEs. Changing schema fields silently changes dedup/merge behavior.
- `schemas.py` reads all agent prompts from `agents.yaml` at import time.
- `settings.py`: `communities_to_analyze = None` means all communities; list of ints restricts. Container image tags are always derived as `vulnscan-<dirname>:latest`. `sandbox_url` is NOT configured here — the preprocessor derives it at runtime and stores it in `MasterState` (together with the sandbox `container_name` in `sandbox_container`, which the Patcher's docker-cp resync needs; the URL itself is the bridge-gateway form of that container's published port).
- `.langgraph_api/` is langgraph runtime checkpoint state (created by `langgraph dev`) — do not commit.
- A previous scan's `report_<YYYY-MM-DD_HHMMSS>/` dir left inside the TARGET APP tree (the reporter writes it there) is auto-excluded from scanning by `utils._DEFAULT_EXCLUDE_DIR_GLOBS`: graphify otherwise extracts its bundled PoC scripts as application source and the scanner "discovers" its own old PoCs as vulnerabilities, which then flow through validate/patch as records whose vuln_id starts with `report_`. This is a full-component fnmatch in `is_path_excluded` pinned to the exact timestamped name the reporter mints (a loosely `report_`-prefixed app dir like `report_generator/` is NOT blinded), honored by every consumer (explorer dispatch, keyword corpus, boundary edges, reviewer reads, patcher, credential finder) — but an already-extracted contaminated `graph.json` needs a re-extract to lose the bogus nodes.
- `states/`, `graphify-out/` are gitignored runtime outputs.
